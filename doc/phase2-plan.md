# Phase 2 实施计划

## 基线与提交边界

- 继续使用本仓库；`final` 保留为 Phase 1 基线，全部完成后在最终提交标记 `p2`。
- 每个提交只记录已完成且可验证的状态。新增插件时保留该提交的路径差异，作为内核无需修改的证据。
- 基础会话以 `doc/transcript/cli-1.txt` 和 `other.svg` 为输入。其输出须在禁用可选插件时与 `final` 逐字节比较。box、stats、dir 的会话在实现对应功能时分别补齐。
- 每个节点运行类型检查及相关测试；框架节点还要运行全部 Phase 1 回归测试。

## 职责与依赖

| 边界 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| 领域模型 | 图形行为、容器关系、唯一 id 和 box 结构不变量所需的通用约束 | CLI 文案、文件系统、插件装载 |
| 应用层 | 会话状态、命令执行、属性修改事务、undo/redo | 具体插件名称、XML 解析 |
| CLI | 分词、输入输出与错误呈现 | 图形类型分派、属性语义 |
| SVG 编解码 | XML 与图形树转换，调用图形提供者处理扩展类型 | 硬编码可选图形类型 |
| 组合根与加载器 | 装配内置能力、解析配置、校验插件清单并提交注册 | 命令和图形的业务行为 |
| VS Code 扩展 | Explorer 标记及原生 Outline 的文档符号 | 修改 SVG 文件名或文件内容 |

插件只依赖公开的领域抽象与扩展接口。默认装配提供 Phase 1 的六种图形及全部命令，不依赖可选插件。扩展接口放在内核侧；实现和配置加载器放在内核外。内置命令同样通过注册表进入分发路径。

## 四个扩展点的预定契约

| 扩展点 | 调用位置 | 契约要点 | 无可选扩展时 |
| --- | --- | --- | --- |
| `ShapeProvider` | `create`、SVG 读回与写出 | 创建完整子树；校验类型、参数和读回标记；由文档一次检查全树 id | 六种内置图形仍可创建、读写 |
| `Command` | CLI 命令注册表 | 提供名称、用法、帮助和执行；明确只读命令不进入撤销历史 | Phase 1 命令照常运行 |
| `TreeDecorator` | 树行格式化阶段 | 按注册顺序返回行尾标签；实例自行保存状态；无标签不添加空格 | `tree` 输出逐字节不变 |
| `AttributeHandler` | `set` 的领域操作阶段 | 只读匹配；命中唯一处理器才执行；重复命中报冲突；失败回滚，不回退默认规则 | 使用 Phase 1 图形属性规则 |

框架节点须完成接口与调用位置，然后在 `doc/README.md` 写出实际文件名、函数名、实现类、缺省行为和违约错误。表中调用位置是目标，不作为尚未编写的代码证据。

## 关键设计决定（实施前）

1. **属性事务**：一次 `set` 是一个 undo 单元。执行前保存目标子树的可变状态；处理器部分修改后抛错，恢复状态，undo/redo 栈不变。处理器只通过公开的图形操作与查询接口访问子部件。若修改会改变树结构，应在接口契约中禁止，或使用覆盖结构的事务边界，不能只恢复属性。
2. **冲突处理**：同一图形和属性由多个处理器声明负责时拒绝本次操作，并报告冲突；注册顺序不决定胜者。没有处理器命中才调用原有 `Shape.set`。
3. **读回策略**：没有 box 插件时，把带 `data-kind="box"` 的元素作为普通 `g` 读入，并保留可表达的子图形；装有插件但缺少必要子部件或类型错误时拒绝整次读取。重复 id 始终拒绝。读入成功后才替换当前文档。
4. **box 不变量**：由通用容器操作契约阻止移走、删除或解组受保护的必要子部件；不能在 CLI 中按 `box` 名称加分支。创建前校验 `id`、`id-rect`、`id-label` 的全树冲突。
5. **dirty 标签**：按当前内容与最近成功保存的内容是否一致判定；撤销回保存点后 `*` 消失。新建节点算修改；修改子图形不自动给祖先加星号。标签按注册顺序拼接。状态保存在装饰器实例中。这些选择须经真实测试后写成 ADR。
6. **装载事务**：代码装配与配置装配共用暂存注册、清单校验、重复检测、提交或回滚流程。按配置顺序激活；失败仅取消当前插件的暂存注册，继续装入后续插件。

## 提交顺序与完成条件

1. `docs: plan phase 2 architecture and baseline`：本计划、Phase 1 输入与独立 SVG 样例、基线测试记录。
2. `feat: add VS Code SVG badge and outline`：文件标记、大纲定位与编辑更新、异常 XML 测试、截图和模式分析。
3. `refactor: introduce plugin extension points`：四个接口、内置实现注册化、Phase 1 回归、首次脚本化 metrics。
4. `feat: add transactional plugin loading`：两种装配共用注册路径；四类加载失败、重复注册和回滚测试。
5. `feat: add stats and dir plugins`：独立插件包；dir 的目录接口、测试替身、真实文件系统测试。
6. `feat: add box plugin through code composition`：只新增插件并修改顶层装配文件；验证内核及既有插件差异为空。
7. `feat: demonstrate box config composition`：从第 5 步的框架基线另开演示分支，加入同一 box 插件并只修改配置；已有运行代码无差异。与第 6 步的代码装配提交分别核对差异，避免在一个提交中切换装配方式。
8. `feat: add composable tree labels`：两个标签并存；无标签的树基线不变，保存点状态机通过测试。
9. `docs: complete phase 2 verification`：PlantUML 前后依赖图、至少三条 ADR、脚本生成的 metrics、完整会话与双装配字节比较，最后打 `p2`。

装入新插件时，检查 `git diff --name-status C^ C`；排除新插件目录后，再检查内核和既有插件路径差异。测试与文档可以随提交增加，但不能把运行逻辑改动藏在这些目录中。

## 设计验收

新增一种图形应只新增提供者及其插件文件，并在装配处选择它；新增命令或标签同理。修改既有功能时，以职责归属决定修改位置，不追求机械的“零文件改动”。每个插件能使用测试替身独立测试；失败操作保持文档及撤销历史原样。模式以解决变化点为准：图形树用 Composite，撤销用 Command，`dir` 的文件访问用 Adapter，树标签用对象组合。
